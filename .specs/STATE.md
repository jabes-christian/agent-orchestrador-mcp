## Decisions

| ID | Decisão | Status | Contexto |
| --- | --- | --- | --- |
| AD-001 | Transporte MCP no fio interno do compose é **Streamable HTTP**. Cada MCP server oficial (stdio-only na forma distribuída) roda em seu próprio container atrás de um shim FastMCP (`create_proxy`) que traduz stdio→Streamable HTTP. O transporte SSE/HTTP+SSE nunca é usado — está deprecado na spec MCP (revisão 2025-11-25). | active | `.specs/features/mcp-orchestrator/design.md` §1.2 |
| AD-002 | O grafo do orquestrador é um `StateGraph` **customizado** do LangGraph (nós/arestas próprios), não um agente prebuilt (`create_agent`/ReAct pronto). Necessário para controle explícito de `iterations`, `trace.steps` por chamada e bloqueio pré-execução da allowlist. | active | `.specs/features/mcp-orchestrator/design.md` §1.1 |
| AD-003 | Acesso ao LLM via OpenRouter usa o pacote dedicado `langchain-openrouter` (`ChatOpenRouter`), não `ChatOpenAI` com `base_url` sobrescrito — a doc oficial do LangChain desaconselha essa rota para providers não-OpenAI. | active | `.specs/features/mcp-orchestrator/design.md` §1.6 |
| AD-004 | A suíte de avaliação de roteamento (MCPO-10) roda em dois modos: modo CI (default, offline, fixtures de resposta do LLM gravadas uma vez) dentro do gate de PR; modo live (`EVAL_LIVE=1`, chamada real ao OpenRouter) fora do gate. Mudar o prompt de decisão exige regravar as fixtures na mesma task. | active | `.specs/features/mcp-orchestrator/design.md` §1.5 |
| AD-005 | Nenhum nome de MCP server ou de tool pode aparecer hardcoded fora de `config/servers.yaml` + `src/orchestrator/mcp_client/registry.py`. Sustenta MCPO-02 AC4 e o Success Criterion "adicionar um terceiro server não exige alterar o pacote do grafo". | active | `.specs/features/mcp-orchestrator/design.md` §1.3 |
| AD-006 | MCPO-12 (limite de custo/tokens por request) é adiado formalmente para v1.1 e não vira task nesta feature. O AC do requisito exige `error.code = "TOKEN_BUDGET_EXCEEDED"`, código ausente do catálogo fechado de 8 erros já validado na Fase 3 (spec); reabrir esse contrato de API por um requisito P3 não se paga. Os limites já existentes (`MAX_REACT_ITERATIONS=5`, `REQUEST_TIMEOUT_S=120`) já fornecem um teto grosseiro de custo por request. | active | `.specs/features/mcp-orchestrator/spec.md` → Requirement Traceability (MCPO-12, status `Deferred`); `.specs/features/mcp-orchestrator/tasks.md` → Requisitos fora do escopo destas tasks |
| AD-007 | `mcp_client.registry` não conhece `tool_policy.yaml` — `ServerInfo.tools[].write` que ele produz é um placeholder `False`, documentado inline. A classificação real de escrita só existe em `mcp_client.policy` (T10). `GET /servers` (T15) é o único ponto autorizado a sobrescrever esse placeholder com `policy.is_write()` antes de responder ao cliente, conforme MCPO-02 AC3 exige `write: bool` correto. Corrigido em `tasks.md` (T15 ganhou `Depends on: T10`) durante a revisão do Lote 1 do Execute, antes de T15 ser implementada no Lote 2 — nenhum código já commitado precisou mudar. | active | `.specs/features/mcp-orchestrator/tasks.md` → T15; `src/orchestrator/mcp_client/registry.py` (comentário inline) |
| AD-008 | `graph.nodes.tools` (T21) não levanta exceção quando uma falha de transporte persiste após o retry — preenche `error: ErrorInfo` no estado retornado em vez disso. Motivo: LangGraph só mescla ao estado o que um nó *retorna*; levantar exceção (como `agent` faz para `LLM_PROVIDER_ERROR`) perderia os `steps` já acumulados nessa chamada do nó, violando MCPO-04 AC2 ("registrar a tentativa falha em trace.steps"). Isso diverge do diagrama de `design.md` §1.2, que desenha `tools` com uma única aresta de saída (de volta a `agent`) — `graph/builder.py` (T24) precisa de uma aresta condicional extra depois de `tools` (`error` preenchido → `finalize`), simétrica à aresta `guard --deny--> finalize` já desenhada no diagrama original. Encontrado durante a implementação de T21 no Lote 3 do Execute; `design.md` §1.2 ainda não foi atualizado com a aresta nova — fica para quando T24 montar o `StateGraph`. | active | `src/orchestrator/graph/nodes.py` (comentário `SPEC_DEVIATION` inline, T21); `.specs/features/mcp-orchestrator/design.md` §1.2 (diagrama a complementar em T24) |
| AD-009 | `api.routes_tasks` (T25) invoca o grafo via `graph.astream(..., stream_mode="values")`, guardando o último snapshot de estado emitido a cada passo, em vez de `graph.ainvoke(...)` como `design.md` §1.5 nomeava literalmente. Motivo: a mesma seção exige que a resposta `REQUEST_TIMEOUT` (504) carregue "o trace parcial acumulado até o ponto do cancelamento (steps já executados continuam no trace)" — cancelar um `ainvoke()` não devolve nenhum estado parcial, as duas frases eram logicamente incompatíveis. Confirmado com o usuário durante a implementação de T25 (Lote 4): optou por manter a exigência de trace parcial (peso de contrato, MCPO-04 AC1/AC2) e corrigir a menção a `ainvoke` em vez do caminho oposto. `design.md` §1.5 e a tabela de Error Handling Strategy já foram corrigidas para nomear `astream`. | active | `.specs/features/mcp-orchestrator/design.md` §1.5, Error Handling Strategy; `src/orchestrator/api/routes_tasks.py` (comentário `SPEC_DEVIATION` inline, T25) |
| AD-010 | Construir um `ChatOpenRouter` real (`llm.provider.get_chat_model`, que internamente instancia `openrouter.sdk.OpenRouter`) em um event loop asyncio e depois usar QUALQUER outro recurso `asyncio`/ASGI em um event loop diferente, no mesmo processo, corrompe esse segundo loop (sintoma: `ERROR: ASGI callable returned without completing response.` seguido de hang indefinido em um servidor `fastmcp`/`uvicorn` completamente não relacionado). Reproduzido isoladamente (fora do pytest) com um script mínimo: a falha desaparece ao trocar `get_chat_model(settings)` por um dublê sem SDK real -- é um bug de afinidade a event loop no SDK `openrouter`/`httpx` subjacente, não um bug deste projeto. Impacto: `main.py` (T25) agora constrói o modelo no `lifespan` de TODA app criada por `create_app()`, então qualquer teste de integração que chame `create_app()` sem passar `model=` explícito passa a rodar `ChatOpenRouter` real e pode travar o *próximo* teste async do processo (não necessariamente ele mesmo). Mitigação: `tests/integration/mcp_test_server.NeverInvokedChatModel` é o dublê padrão -- todo `create_app(...)` em teste que não exercita `POST /tasks` de propósito DEVE passar `model=NeverInvokedChatModel()` (aplicado em `test_main.py`/`test_routes_servers.py` durante T25); tasks futuras que chamem `create_app()` sem precisar do LLM real (T26 `GET /health`, testes de Docker/E2E que não sejam o smoke test) devem seguir o mesmo padrão. | active | `tests/integration/mcp_test_server.py` (`NeverInvokedChatModel`); `tests/integration/test_main.py`, `tests/integration/test_routes_servers.py` (uso do dublê); `src/orchestrator/main.py` (`create_app(model=...)`, T25) |
| AD-011 | Mesma classe de bug do AD-010, gatilho diferente: uma PRIMEIRA conexão MCP real que efetivamente INVOCA uma tool (não apenas `registry.discover()`/listagem, que é seguro -- `test_registry.py` já faz isso repetidamente sem problema) via `MultiServerMCPClient`/`langchain-mcp-adapters`, seguida por QUALQUER nova conexão MCP real (mesmo só um `discover()`) em um event loop asyncio diferente no mesmo processo, trava a segunda indefinidamente (mesmo sintoma: `ERROR: ASGI callable returned without completing response.`). Reproduzido isolado, fora do pytest, com script mínimo. Trocar `asyncio_default_test_loop_scope`/`asyncio_default_fixture_loop_scope` para `module` NÃO resolve (pytest-asyncio 1.4.0 continua criando um `asyncio.run()` novo por teste nesta config). Mitigação adotada: `main.py.create_app()` ganhou o parâmetro `tools_by_server` (T25) -- quando fornecido, `build_graph()` usa essas tools diretamente (dublês, sem conexão MCP real), no mesmo padrão de `tests/unit/test_builder.py`, contornando o SDK em vez de tentar consertá-lo. Regra para tasks futuras: no máximo UM teste por arquivo/processo pode fazer uma invocação de tool real via `MultiServerMCPClient`; qualquer outro teste que precise de um step real no trace deve usar `tools_by_server` com uma tool falsa (ver `_FakeReadFileTool` em `tests/integration/test_routes_tasks.py`) em vez de `run_fake_mcp_server` + `server_configs`. | active | `src/orchestrator/main.py` (`create_app(tools_by_server=...)`, T25); `tests/integration/test_routes_tasks.py` (`_FakeReadFileTool`, teste de timeout) |
